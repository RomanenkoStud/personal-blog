# Adapter: Cloudflare D1 (SQLite)

- Migrations: `<dir>/NNNN_name.sql`, applied by `wrangler d1 migrations apply` in filename order, tracked by filename in `d1_migrations`. A failed file is rolled back; earlier files in the same run stay applied (see `applied.txt`).
- Snapshot: `.heal/snapshot/remote-schema.sql` (`wrangler d1 export --no-data`) and `applied.txt`.
- **Verify:** run `verify_command` from `.heal/context.json` verbatim (it is the only allowlisted form). It rebuilds a local D1 from the snapshot each run and applies pending migrations.
- Inspect after a verify run: `npx wrangler d1 execute <database> --local --persist-to .wrangler/self-heal-state --command "SELECT sql FROM sqlite_master"`, with `<database>` from `.heal/config.json` → `migrations.d1.database` written literally (no shell variables — permissions match the literal command).

SQLite / D1 limitations that commonly cause failures:
- `ALTER TABLE` supports only `ADD COLUMN`, `RENAME COLUMN`, `RENAME TO`, `DROP COLUMN` (and the latter fails if the column is indexed, part of a constraint, or referenced). Adding constraints / changing types needs the rebuild pattern: `CREATE TABLE x_new (...)` → `INSERT INTO x_new SELECT ... FROM x` → `DROP TABLE x` → `ALTER TABLE x_new RENAME TO x` → recreate indexes/triggers.
- `ADD COLUMN ... NOT NULL` requires a non-NULL `DEFAULT`.
- No `IF NOT EXISTS` for `ADD COLUMN` — for "duplicate column" errors on a pending migration, the column already exists remotely: remove that statement from the pending migration (note it in the summary).
- No `BEGIN`/`COMMIT` in migration files (D1 wraps each file); `PRAGMA foreign_keys` is ignored — use `PRAGMA defer_foreign_keys = true` around rebuilds.
- Max SQL statement size 100 KB.
